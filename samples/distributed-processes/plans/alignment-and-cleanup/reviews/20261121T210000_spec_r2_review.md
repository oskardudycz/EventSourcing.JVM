### Q&A-1. The process manager style's guest account is an aggregate, and the spec deletes its base classes

Quote: "The hotel examples already use deciders and records, except the process manager"; "Their deciders, records, names and structure stay."; "`AbstractAggregate`, `Aggregate`, `AggregateStore` ... are deleted."
Consequence: `processmanager/gueststayaccount/GuestStayAccount` extends `AbstractAggregate`; its `GuestStayAccountService` uses `AggregateStore` and `EventBus`. The developer must either rewrite it as a record with a decider (more than Q10 allows) or keep the aggregate classes (against the deletion).
Belongs to: qa
Resolution: from Oskar: "don't change anything in the hotel management examples or business code unless it's required ... focus on the ecommerce. only align what's needed in core". Fixed in r3: the aggregate classes stay in core for the hotel, adapted to the new store types only.

### Q&A-2. Keeping the process manager "as it is" leaves criterion 7.1 impossible for that style

Quote: "Internal events reach the saga and the process manager through `EventStore.subscribe`"; criterion 7.1 "...and the process manager style THEN both guests are checked out and the group checkout completes."
Consequence: Nothing creates, stores or starts `GroupCheckoutProcessManager` (only the static `initiate(...)`); its status fields are private and it records no completion event. The developer must invent storage, a starter and an observable result, all new hotel code.
Belongs to: qa
Resolution: fixed in r3: no hotel business tests (Q11); criterion 7 removed.

### Q&A-3. The choreography style's event delivery is not stated

Quote: "Internal events reach the saga and the process manager through `EventStore.subscribe`, as in the shop."
Consequence: The choreography `GroupCheckoutService` has three event handlers fed through the deleted `EventBus`; store subscription or bus subscription is a guess.
Belongs to: spec
Resolution: fixed in r3: the hotel code is not changed (Q11), so its event delivery stays as it is.

### Q&A-4. The generic decider rules say "each entity", but the hotel deciders differ

Quote: "Each entity is a record with a static `initial()` and `evolve(state, event)` ... returning a list of events ... late or repeated commands produce no events and don't throw".
Consequence: Hotel deciders return arrays and `Optional`, use `empty()`, and throw on a repeated check-in (a hotel test checks it). A developer could change them, against Q10.
Belongs to: spec
Resolution: fixed in r3: the decider rules apply to the four shop modules only.

### Q&A-5. r2 contradicts itself on events with an unknown type name in a subscription

Quote: "A read that meets an event it can't map fails with `UnreadableMessageException`; a subscription that meets one treats it as a handler failure." against "An event with an unknown name is passed over" and criterion 4.3.
Consequence: Following the first sentence, a subscription retries an unmapped event forever.
Belongs to: spec
Resolution: fixed in r3: the event store contract sentence now matches criteria 4.2 and 4.3.
