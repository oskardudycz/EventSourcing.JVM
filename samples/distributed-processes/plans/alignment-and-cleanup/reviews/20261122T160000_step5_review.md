### Step-1. PaymentDecider throws for a command in its own sealed interface

Quote: diff `PaymentDecider.handle`: `case CreateCheckoutSession ignored -> throw new IllegalArgumentException("Creating a checkout session is not decided on the payment");`; test `PaymentTests.creatingACheckoutSessionIsNotDecidedOnThePayment ... .thenThrows(IllegalArgumentException.class)`. Spec: "The rule that late or repeated commands produce no events and don't throw stays". Neither `spec.md` nor `qa.md` mentions `CreateCheckoutSession` or `RecordCheckoutSession`.
Consequence: the new public command `PaymentCommand.RecordCheckoutSession` has no basis in the step or spec. If `CreateCheckoutSession` ever reaches the command handler, it throws, and a test pins that throw. The facade also records the session at the time the decider runs, not at the `createdAt` taken before the gateway call; this only matters in a corner case, as the session is valid for 30 minutes.
Belongs to: plan. The step does not say how `createCheckoutSession` (a gateway call plus a write) fits the decider model. Choices: a separate command (as built), move `CreateCheckoutSession` out of `PaymentCommand`, or a no-op case.
Resolution: fixed (coordinator decision): `CreateCheckoutSession` leaves the sealed `PaymentCommand`, because the spec says `PaymentFacade.createCheckoutSession` only reads the payment with `get(id)`; the decider throw and its test go. `RecordCheckoutSession` stays: it replaces the old aggregate method `recordCheckoutSession`.

### Step-2. Error branches of CommandHandler that no test runs

Resolution: accepted (coordinator): the step asks for no test of these branches; they pass the store's failure through.

### Standards-2. `handleOnce` takes a boolean flag and a boxed `Long`

Quote: `private long handleOnce(Id id, Command command, Long clientVersion, boolean continuingTrace)`, called as `handleOnce(id, command, null, true)`; `clientVersion != null ? ... : ...` appears twice.
Consequence: call sites read as `null, false` and `null, true`; a flag selects behaviour. No wrong behaviour: parity with the old `AggregateStore.update` was checked (no events returns the client version, or the version read, and version 0 is handled). The implementer already lists it as open.
Belongs to: implementation
Resolution: accepted (coordinator): a private method; no wrong behaviour found.

### Standards-3. Duplicated retry template and `describe` code in CommandHandler and AggregateStore

Quote: both declare `private static final RetryTemplate retry = new RetryTemplate(RetryPolicy.builder().includes(ConcurrentModificationException.class).maxRetries(2).delay(Duration.ZERO).build());`, and both have `describe(long)`, `describe(ExpectedStreamVersion)` and the same four-way `AppendResult` switch with the same error texts.
Consequence: changing the attempt count or a message means two edits, and the two can drift apart. No wrong behaviour today. The plan asks for "the same `RetryTemplate`" and says to avoid new abstractions unless asked, so the duplication is defensible; this is Oskar's call.
Belongs to: implementation
Resolution: accepted (coordinator): the spec keeps `AggregateStore` for the hotel and asks for no new shared abstraction.
