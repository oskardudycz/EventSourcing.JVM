### Q&A-4. Store subscriptions retry an unreadable event forever, a behaviour change no answer chose

Quote: Criterion 4.2; message-broker spec: "no retry for a message that can't be read, then the queue's dead-letter destination."
Consequence: One unreadable event would stop that projection or forwarder for good; after a rename without an explicit name, every subscription to that type stops.
Belongs to: qa
Proposed: see Quality-3. A subscription takes only the type names that map to its classes, so an event with an unknown name is not its event and is passed over, as today. An event whose name maps to a subscribed class but fails to deserialize is a handler failure and is retried, because skipping it would lose an event the subscriber needs. A stream read (`CommandHandler`) fails on any unreadable event (S3).
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-1. Type names: two Java "class names", and sub-packages the brokers won't trust

Quote: "the type name is the Java class name"; "Each module's config registers a `MessageMapping` for its package: the package is trusted"; criteria 5.1, 3.1.
Consequence: For nested records, `Class.getName()` gives `...PaymentEvent$PaymentAuthorized` (what Spring writes in `__TypeId__`), the canonical name gives `...PaymentEvent.PaymentAuthorized`; stores and buses could use different forms. External events live in sub-packages (`payments.external`); spring-amqp's `DefaultClassMapper` matches trusted packages with `equals`, spring-kafka with a simple pattern, so external events would be dead-lettered as untrusted.
Belongs to: spec
Proposed: the type name is `Class.getName()` (with `$`) everywhere, as Spring writes it; criteria 5.1 and 3.1 give an example value. A module trusts its package and every sub-package that holds a message class; the mapper lists each package explicitly, because Spring AMQP matches exactly.
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-2. Where module mappings are registered, given the current wiring

Quote: "Each module's config registers a `MessageMapping` for its package ... `ECommerceMessages` is deleted."; "`MessageSerializer` is one bean".
Consequence: Module configs are static methods that run after the bus and store beans exist; Spring's type mappers copy the name map at creation; about 10 tests build buses from `ECommerceMessages.mapping()`.
Belongs to: spec
Proposed: each module config has a static `mapping()` returning its `MessageMapping`; `ECommerceApplicationConfig` builds the `MessageTypeMapper` from the four module mappings (and the hotel examples' tests from theirs) before it creates the serializer, the buses and the stores; tests use the same module mappings through `TestMessages`.
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-3. Subscriptions filter by type, but old names and unreadable events are not covered

Quote: "an old name may map to the current class with a transformation"; "it filters types in Java"; criteria 4.2, 5.3.
Consequence: Filters match names today (KurrentDB server-side regex, PostgreSQL in SQL); a transformation doesn't declare the class it produces, so the mapper can't list a class's old names; deserializing every event on every poll would add work no answer allows.
Belongs to: spec
Proposed: a transformation registration names the class it produces (`register(oldName, OldClass, CurrentClass, transform)`, and the `JsonNode` variant likewise), a small change to the workshop's signature, so the mapper knows every name of a class. A subscription filters on those names: KurrentDB keeps its server-side filter, PostgreSQL filters names in Java after reading the batch (S8). Unknown names are passed over (Q&A-4).
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-5. One position, three names; which event's position the append returns

Quote: "`GlobalPosition(long transactionId, long position)`"; "`Checkpoint`"; "`EventMetadata` keeps its fields"; "`Success(long nextStreamVersion, GlobalPosition position)`"; criterion 2.1.
Consequence: `Checkpoint(long transactionId, long position)` already exists with the same shape; `EventMetadata.logPosition` holds the same value; the function returns several positions but `Success` holds one.
Belongs to: spec
Proposed: no `GlobalPosition`; `Checkpoint(transactionId, position)` is the one type. `AppendResult.Success(long nextStreamVersion, Checkpoint lastEvent)` holds the last appended event's checkpoint. `EventMetadata` keeps `logPosition` and gains `transactionId`, so subscribers get the full checkpoint.
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-6. Settings of the one `JsonMapper`

Quote: "`MessageSerializer` is one bean with one `JsonMapper` ... so a message round-trips the same everywhere".
Consequence: The in-memory store keeps the `OffsetDateTime` offset (`ADJUST_DATES_TO_CONTEXT_TIME_ZONE=false`, field visibility ANY); KurrentDB and PostgreSQL normalize to UTC; in-memory business tests compare events built from `OffsetDateTime.now()`.
Belongs to: spec
Proposed: one `JsonMapper` bean with `FAIL_ON_UNKNOWN_PROPERTIES=false`, `WRITE_DATES_AS_TIMESTAMPS=false` and `ADJUST_DATES_TO_CONTEXT_TIME_ZONE=false`, so every store and broker keeps the offset as written; Spring's broker serializers get the same mapper, as in the workshop (`MessageSerializationConfiguration` passes the `JsonMapper` bean). Field visibility ANY goes; messages are records.
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).

### Quality-7. Decider signature against what the entities use today

Quote: "a `<Name>Decider` with static `handle(command, state)` functions"; "Facades call command handlers."
Consequence: The cart prices items with `ProductPriceCalculator`; payment commands carry no time and the facade adds `now` and `paymentValidity`; `PaymentFacade.createCheckoutSession` and `ShoppingCartFacade.isCheckedOut` read state without a command.
Belongs to: spec
Proposed: as the reference (`event-sourcing-kurrentdb-simple`: `new ShoppingCartDecider(productPriceCalculator)`), a decider is an instance when it needs dependencies (price calculator, clock, payment validity and terms), with `handle(command, state)` methods; otherwise its methods are static. `CommandHandler` has `get(id)` returning the folded state, used by the two read-only facade methods.
Resolution: fixed in r2 as proposed (Oskar did not object to the proposals).
