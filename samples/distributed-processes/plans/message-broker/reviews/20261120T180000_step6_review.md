### Step-1. `aCancelledSubscriptionSubscribesAgainFromItsCheckpoint` may pass without the `onCancelled` and resubscribe path

Quote: the test stores `checkpoints.handle(name, 1, () -> {})`, calls `store.subscribe(name, ...)`, then moves the checkpoint with `checkpoints.handle(name, ((EventStore.AppendResult.Success) earlier).logPosition().getCommitUnsigned(), () -> {})` and expects `containsExactly(new ItemAdded(cartId, "t-shirt"))`. Code: `options.fromPosition(new Position(c, c))`. Step: "A subscription whose handler fails stops and resubscribes from its checkpoint after `RetryBackOff`."
Consequence: the test never makes a handler fail and cancels nothing itself. It reaches `onCancelled` only if KurrentDB rejects position 1. If the server accepts it, the subscription starts there, delivers the event at once, and the test passes with `onCancelled` and `fail(...)` deleted. If `optionsAfterCheckpointOf` ignored the checkpoint and used `fromStart()`, the test would also pass, because the event is appended before the subscription starts. The `onCancelled` branch with a throwable is then untested. Plausible, not confirmed (reviewers could not check how the server treats a non-boundary position). `subscriptionContinuesAfterItsCheckpointOnRestart` still covers the checkpoint start. Fix: force a real cancellation and assert that it happened, or assert that the first start failed; or rename the test to what it proves.
Belongs to: implementation
Resolution: fixed. The test now asserts that nothing is delivered for one second while the checkpoint is at the invalid position, then moves the checkpoint and asserts the delivery. If the server accepted the position, or the subscription started from the start, the event would arrive in the first window and the test would fail.
