### Spec-1. Criterion 35 is never tested on Kafka or RabbitMQ, and the workshop code that the plan copies breaks it

Quote: Spec, Testing Decisions: "**`MessageBus`:** one shared test set ... runs for in-memory, Kafka and RabbitMQ (criteria 6-9, 15, 35)." Plan step 3 tests 35 only in memory; steps 7 and 9 don't list 35; step 7 copies "`messages/MessageMetadata.java`".
Consequence: The workshop's `MessageMetadata` sets a new random ID on each publish (`sagas_kafka/core/messages/MessageMetadata.java:28`). Copied as is, a redelivered event goes out on a broker with a new `messageId` (review N3), and no test catches it.
Belongs to: plan
Resolution: fixed in r3: 35 is in the Kafka step (8) and the RabbitMQ step (10) with header tests; step 8 copies `MessageMetadata` without its random `messageId`.

### Spec-2. The spec does not agree with itself on where the view tests run, and the plan picks H2 only

Quote: Spec: "`ProjectionTests` and the view tests run on JPA with PostgreSQL and with H2 (criterion 29)." and "... and the view tests get their repositories the same way (Q25)." Plan step 2: "they get repositories from a Spring context on H2, and `ProjectionTests` runs on both databases."
Consequence: The query methods of nine views would never run on PostgreSQL, the default database.
Belongs to: spec
Resolution: fixed in spec r18 and plan r3: criterion 29 and the Projections line say both databases, so the view tests run on both; the ECommerceTests line no longer names the view tests.

### Spec-3. Nothing opens the step span for "Pay now" and "Retry payment", because they do not go through the bus

Quote: Spec: "One span per handler call is a step. The bus's consumer and the store's subscription open it around the handler". Spec: "'Pay now' (`CreateCheckoutSession`) and 'Retry payment' (`RetryOrderPayment`), continue the trace from the last event of the order's stream".
Consequence: Both are direct facade calls on the HTTP thread (`OrdersController.java:66-67`, `:82`), so no step span exists for 33.2 and 33.3. `PaymentFacade` is in the payments module and has no access to the order's stream.
Belongs to: spec
Resolution: open, plan item P1 for Oskar. Step 12 leaves 33.2 and 33.3 out until it is answered.

### Spec-4. Step 9 does not build or test the spec's rule that publishing to an undeclared channel fails on RabbitMQ

Quote: Spec: "A publish to a channel that is not declared fails, on all three buses (criterion 10; Q25)." Plan step 9 has no undeclared-channel case.
Consequence: On RabbitMQ the publish would fail only through a channel error or a confirm time-out, not at once with the channel's name.
Belongs to: plan
Resolution: fixed in r3: step 10 builds it and tests `publishToAnUndeclaredChannelFailsNamingTheChannel`.

Mechanical: steps listing sub-criteria covered elsewhere now name the covering step; step 8 (Kafka failures, now 9) is blocked by the checkpoint step; the RabbitMQ step no longer claims to run in parallel; the Compose profiles of Kafka, RabbitMQ and LGTM are named; the Grafana step names its setup. All fixed in r3.

### Steps-1. Step 1 breaks OrderSagaTests and two forwarder tests that use a bare bus

Quote: "Module and facade tests that build a bus by hand: they go through the module configs, which now declare channels."
Consequence: `OrderSagaTests` and two forwarder tests build `new InMemoryMessageBus()` with no routes; after step 1 every publish throws. Which module declares `payments-requests` was not decided.

Resolution: fixed in r3: those tests register the routes and channels of the messages they publish in their own setup, with no subscribers; the module whose config holds a route declares its channel (Terms, Route).

### Steps-2. Step 2 puts the worker views on a shared database, so worker tests see other tests' documents

Quote: "The projections store their documents through JPA, on H2 or PostgreSQL".
Consequence: Worker queries return every matching document; on a shared database worker tests pick up other tests' documents and their exact-message assertions fail.
Belongs to: plan
Resolution: fixed in r3: worker tests assert only on messages about their own new IDs, as AGENTS.md's shared-database rule implies; the aggregates ignore commands for streams that don't exist in the test's store.

### Steps-3. The `in-memory` profile is used from step 2 but created in step 14, and step 14 misses the API tests

### Steps-4. Step 2 joins two areas that could each be merged alone

### Steps-5. Step 3's message metadata can't be observed on the in-memory bus

Quote: "35.1: ... both publishes have the same `messageId`." / "aMessageWithNoCauseGetsARandomMessageId - an HTTP command and a worker command each get a new random `messageId`."
Consequence: Subscribers get only the payload, so a test can't read a message's `messageId` without a new API; HTTP commands don't go through the bus; "the forwarder fails once" gives two publishes only if the failure is after the publish.
Belongs to: spec
Resolution: fixed in r3: in-memory tests observe the values through the events the handlers append, read back with their metadata; 35.1's failure is in a subscriber of the published message; the HTTP-command test checks the appended events' `causationId` equals their `correlationId`; header-level checks move to the broker steps.

### Steps-6. Registering the global OpenTelemetry breaks step 3's KurrentDB checks and can fail later Spring contexts

Quote: Step 3: "asserts the five values match, on in-memory and KurrentDB." Step 13: "registers Spring Boot's `OpenTelemetry` as the global one".
Consequence: With the global set, KurrentDB stores its append span's ID in `$spanId`, so 28.1 fails depending on test order; `GlobalOpenTelemetry.set` throws on a second call in one JVM.
Belongs to: spec
Resolution: fixed in spec r18 and plan r3: 28.1 follows the spec's own KurrentDB decision (findings 2.3): on KurrentDB the `spanId` is the client's append span, child of the current span. Step 14 sets the global only when not set, and its tests use OpenTelemetry's `GlobalOpenTelemetry.resetForTest()`.
