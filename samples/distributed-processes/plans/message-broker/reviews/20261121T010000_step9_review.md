### Step-1. Dead-letter publish is not awaited, so a failed dead-letter send loses the message but still counts it

Quote: `new DeadLetterPublishingRecoverer(failures.deadLetterTemplate(), (record, error) -> new TopicPartition(deadLetterTopicOf(queue), -1))`, then `deadLetters.accept(record, error); failures.meters().counter(DEAD_LETTERED, ...).increment();`. Plan 17: "so that the message is kept for a person to look at".
Consequence: `DeadLetterPublishingRecoverer` does not wait for the send result by default. If the dead-letter publish fails (Kafka down, timeout), the recoverer only logs, the handler treats the record as recovered, the offset is committed, the message is lost and `messaging.dead_lettered` still rises. No test covers it. The spec decides this only for RabbitMQ (criterion 20), not for Kafka.
Belongs to: implementation
Resolution: fixed: Spring Kafka 4.1.2 already fails the recoverer when the send fails, so no main change; test `messageIsNotLostWhenTheFirstDeadLetterPublishFails` guards it

### Step-2. 11.1 does not time the forwarder's publish

Quote: plan 11.1 test: "assert the forwarder's publish fails within the publish timeout plus one second and its checkpoint is unchanged". `forwarderPublishFailsWithinTheTimeoutAndKeepsItsCheckpointWhileKafkaIsDown` waits for `publishAttempts.get() >= 2`, then checks the checkpoint. Timing is only in `publishFailsWithinThePublishTimeoutWhileKafkaIsDown`, on a direct `messageBus.publish(...)`.
Consequence: nothing shows the forwarder's own publish fails within timeout + 1s. The test passes if each forwarder publish blocks long, as long as it retries twice.
Belongs to: implementation
Resolution: accepted by the coordinator: a paused broker cannot show the producer dropping a request already in the socket; the sizing is tested on the producer configuration (`producerTimeoutsFitInsideThePublishTimeout`) and a direct publish is timed

### Step-3. The `messaging.dead_lettered` tags are unbounded and not in the spec

Quote: `.counter(DEAD_LETTERED, "message.type", typeNameOf(record), "messaging.destination.name", record.topic())`; `typeNameOf` returns the raw `messageType` header. Spec 247: "The `messaging.dead_lettered` counter counts each dead letter (Q12)." (no tags).
Consequence: a header value chosen by a sender creates a new Micrometer time series per value, so untrusted input can grow the registry without bound. `messaging.destination.name` is the channel topic for a `#` queue and the queue topic for a narrower pattern, so it does not name the queue consistently. No test checks the tags.
Belongs to: implementation (tags bound), with a spec gap on the tag set. Searched spec.md and qa.md: neither names tags.
Resolution: fixed: `message.type` is the registered stable name or `unknown`, the source topic tag stays; tests `deadLetterCountIsTaggedWithTheStableTypeNameAndTheSourceTopic` and `deadLetterCountOfATypeThatIsNotRegisteredIsTaggedUnknown`

### Step-4. A type name in the trusted package that names no class has no test

Quote: `MessageSerializer.trustedClassOf`: `catch (ClassNotFoundException e) { throw new UnreadableMessageException(typeName, e); }`. Plan 19: "whose type name is unknown or outside the sample's package".
Consequence: the "unknown" half of 19 is untested. If the branch broke, a checked `ClassNotFoundException` would escape and the record would be retried instead of dead-lettered at once.
Belongs to: implementation
Resolution: fixed: test `typeNameInsideTheSamplesPackageThatNamesNoClassIsDeadLettered`

### Step-5. `typeNameOf` falls back to the Java class name

Quote: `return mapping.typeNameOf(messageClass).orElseGet(messageClass::getName);`, pinned by `aMessageWithoutAStableTypeNameIsWrittenUnderItsClassName`. Spec 253: "Every message type that crosses the bus has a stable type name in the mapping. ... The workshop's `eventType` header fallback is not copied (review N8)."
Consequence: an unmapped class is published under its Java name, which is the coupling stable names remove; renaming the class breaks old messages. The spec does not say what happens to an unmapped type. Searched spec.md and qa.md: no decision (only 22.1, which covers a mapped name).
Belongs to: spec
Resolution: fixed: `MessageSerializer.typeNameOf` throws `IllegalStateException` naming the type; `ECommerceMessagesTests` and `MessageSerializerTests.aMessageWithoutAStableTypeNameCannotBeNamed` guard it

### Step-6. The Spring bean wiring of the dead-letter template and retry interval has no test

Quote: `deadLetterKafkaTemplate` only calls `template.setObservationEnabled(true)`; `messageBus` reads `messaging.retry.initial-interval`. Plan: "The dead-letter template is a Spring bean with the observation registry". 17.2 uses `TestKafka.failureHandling`, which calls `setObservationRegistry(observations)` by hand.
Consequence: if the production bean does not pick up the registry, 17.2 stays green and the real application does not trace dead letters. `ECommerceSettingsTests` only checks the bus type. (Same gap as Standards-1.)
Belongs to: implementation
Resolution: fixed: `ECommerceSettingsTests.KafkaDeadLettering` runs the application context with `messaging.bus=kafka` and checks the dead-letter span in the trace and the retry interval from `messaging.retry.initial-interval`
