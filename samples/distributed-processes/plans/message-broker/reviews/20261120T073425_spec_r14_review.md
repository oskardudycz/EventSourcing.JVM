### Q&A-5. The checkpoint skip rule compares positions only, but the PostgreSQL poller reads in transaction ID order

Quote: Q&A Q22, Decision (spec r11): "skip when the stored checkpoint is at or past the new position ... The PostgreSQL poller orders by transaction ID, then `global_position`". The user's answer was only "not a total copy but simple enough". Spec: "When the stored checkpoint is already at or past the new position, the event was handled, so the update is skipped and its transaction rolls back." Spec: "ordered by transaction ID and then `global_position`". Spec criterion 27.5: "GIVEN a stored checkpoint already past a batch ... THEN the checkpoint doesn't change AND the batch's changes are rolled back."
Consequence: The workshop's `append_event` locks the stream row (`SELECT ... FOR UPDATE`, `UPDATE streams`) before `INSERT INTO events` takes `nextval('global_event_position')`. So transaction A can get the lower transaction ID and still get the higher `global_position`, if transaction B on another stream inserts in between. The poller then delivers A (position 2) before B (position 1). After A, the stored checkpoint is 2, and B is "at or past" it, so the projection skips B and rolls it back. The event is lost. This is the kind of loss that Q21's transaction ID guard exists to prevent. The comparison rule is the interviewer's note. Oskar did not decide it.
Belongs to: qa
Resolution: fixed in r15: Q25, the PostgreSQL check compares the transaction ID, then the position.

### Quality-10. A shared subscription name loses events, and per-type subscriptions break the projections

Quote: "`EventStore.subscribe` gets a subscription name, for example `subscribe(\"payments-external-forwarder\", PaymentAuthorized.class, forwarder::onAuthorized)`. The 12 calls in the modules change (Q22)."; "When the stored checkpoint is already at or past the new position, the event was handled, so the update is skipped"
Consequence: The modules make 29 `subscribe` calls: 12 lines start with `eventStore.subscribe(`, and 17 more calls are chained (for example `PaymentsConfig` lines 85-89). Projections also subscribe once per event type, in a loop. Each call is its own subscription: `KurrentDBEventStore.subscribe` makes one `subscribeToAll` with a type filter. If the five forwarder calls share one name, one subscription stores position 100, and another then skips its event at position 90 as already handled, so that event is lost. If each call gets its own name, a projection gets its event types from separate subscriptions that move on at different speeds: `Projection.handle`'s check `getVersion() >= streamPosition` drops an earlier event that arrives late, and `evolve(null, OrderPaymentAuthorized)` throws a NullPointerException when that event arrives before `OrderPlaced`. The developer must choose between one name per call and a `subscribe` that takes several types.
Belongs to: qa
Resolution: fixed in r15: Q25, one subscription per subscriber object; `subscribe` takes several types.

### Quality-11. The PostgreSQL checkpoint check must compare the transaction ID, not only the position
