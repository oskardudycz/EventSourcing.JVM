### Step-1. The repeated-failure test never reaches the back-off STOP branch

Quote: test: `if (attempts.incrementAndGet() < 3) throw new IllegalStateException("projection is down");` with `RetryBackOff.exponential(Duration.ofMillis(100))`. Code: `backOff.setMaxAttempts(2)`; `nextDelay()`: `if (delay != BackOffExecution.STOP) return delay; backOffExecution = backOff.start(); return backOffExecution.nextBackOff();`. Step: "A subscription whose handler fails stops and resubscribes from its checkpoint after `RetryBackOff`."
Consequence: the handler fails twice, so `nextBackOff()` returns 100 ms and 200 ms. STOP comes only on the third failure. If the STOP branch threw, returned a negative delay or ended the subscription, all tests would still pass. The back-off reset after a good event is not checked either. This does not touch the open Step-4 decision: it only checks that the existing code keeps retrying. Fix: fail at least 4 times and assert the event arrives.
Belongs to: implementation
Resolution: fixed. The repeated-failure test fails 4 times with `maxAttempts` 2, so the STOP branch and the restart run.

### Step-2. Nothing guards the `ConditionalOnProperty` and `destroyMethod = "shutdown"` of the `KurrentDBClient` bean

Quote: `@Bean(destroyMethod = "shutdown") @ConditionalOnProperty(name = "eventstore.type", havingValue = "kurrentdb") KurrentDBClient kurrentDBClient(...)`. `ECommerceSettingsTests` asserts only that `eventStore` is a `KurrentDBEventStore` (kurrentdb) and the in-memory beans (default).
Consequence: `KurrentDBClient.create` does not connect, so a client created in every mode, or one never shut down, passes all tests. A regression gives an unneeded gRPC channel in memory mode or leaked threads after the context closes. Fix: in the in-memory profile assert there is no `KurrentDBClient` bean; in the kurrentdb context close it and assert the client is shut down. No step-listed test covers this, so the user may accept the gap.
Belongs to: implementation
Resolution: fixed by removing the cause: the `KurrentDBClient` bean and its `ConditionalOnProperty` are gone. The store created with `connectingTo` owns its client; `closingAStoreThatOwnsItsClientShutsTheClientDown` checks that an append fails after `close()`. The restart tests already show that a store given a client leaves it open.

### Standards-1. `KurrentDBEventStoreTests` never shuts down its `KurrentDBClient`

Quote: `private final KurrentDBClient client = KurrentDBClient.create(KurrentDBConnectionString.parseOrThrow(TestDatabases.kurrentDBConnectionString()));`. Teardown: `@AfterEach void closeStores() { stores.forEach(KurrentDBEventStore::close); }`. `KurrentDBEventStore.close()` closes only the subscriptions.
Consequence: JUnit makes one instance per test method, so each test leaves a gRPC channel and its threads open until the JVM exits. The tests do not apply the lifecycle the step added to main (`destroyMethod = "shutdown"`). Fix: call `client.shutdown()` in `closeStores`.
Belongs to: implementation
Resolution: fixed. `closeStores` calls `client.shutdown()`.

### Standards-2. The `KurrentDBClient` bean style differs from the surrounding config

Quote: `@Bean(destroyMethod = "shutdown") @ConditionalOnProperty(name = "eventstore.type", havingValue = "kurrentdb") KurrentDBClient kurrentDBClient(...)` next to `EventStore eventStore(@Value("${eventstore.type:in-memory}") String type, ObjectProvider<KurrentDBClient> kurrentDBClient, ...)`. It is the only `@ConditionalOn*` in the project; `eventstore.type`, `messaging.bus` and `projections.database` use `switch (type)` and `Settings.unknownValue(...)`.
Consequence: `"kurrentdb"` is decided in two places; a new `eventstore.type` value must be added in both. No wrong behaviour today (`ECommerceSettingsTests` covers it). Low severity: Spring has no `@Bean` form that is created only inside one `switch` case, so keeping the annotation may be the pragmatic choice and the user may accept it.
Belongs to: implementation
Resolution: fixed. The bean and `ConditionalOnProperty` are removed; the `eventstore.type` switch is the only place that knows `kurrentdb`.
