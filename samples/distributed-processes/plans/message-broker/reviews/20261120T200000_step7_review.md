### Step-1. The plan's example for `checkpointComparesTransactionIdBeforePosition` contradicts its own rule

Quote: plan step 7: "a stored checkpoint (transaction 101, position 5) and a new event (transaction 100, position 7): the event is "past"; with (transaction 99, position 9) it is not." Rule in plan and spec: "compares the transaction ID first, then the position."
Consequence: (99, 9) is past under the rule (99 < 101), so the plan sentence cannot be built. The implementation is right (`ProcessorCheckpoint.isAtOrPast` compares the transaction ID first). The tests `positionOfAnEventInAnOlderTransactionIsPastTheCheckpointEvenWhenItIsHigher` (101,5 stored; 100,7 stays past) and `positionOfAnEventInANewerTransactionIsNotPastTheCheckpointEvenWhenItIsLower` (102,3 moves the checkpoint) both fail under a position-only check, so they guard the rule in both directions. The fix is in the plan text: use (102, 3) as the "not past" example. Neither spec.md nor qa.md gives the example.
Belongs to: plan
Resolution: fixed in plan r5 by the coordinator under Q30: the example now uses (100, 7) as past and (102, 3) as not past, as implemented.

### Step-2. The plan says the in-memory store already continues the trace; it does not

Quote: plan step 7: "restores `correlationId` and `causationId` before the handler runs, as step 4's in-memory store does." Spec: "each store's subscription continues the trace from the event and sets the baggage before the handler runs." Code: `InMemoryEventStore.java:133` and `KurrentDBEventStore.java:112` call only `context.handling(messageId, correlationId)` (baggage, no span). Only `PostgreSQLSubscription` calls the new `MessageContext.handling(String, EventMetadata)`, which opens the step span from the stored `traceId` and `spanId`.
Consequence: the step 7 sentence points to behaviour that does not exist, and no step names the work to give the in-memory and KurrentDB subscriptions a step span (step 12 says only "A store subscription continues the trace from the event"). The spec and the plan promise every store does it. qa.md Q25 only says the in-memory store "keeps its behaviour and stores the five metadata values", so it does not decide this. The step 7 code is correct for what step 7 lists.
Belongs to: plan
Resolution: fixed in plan r5 by the coordinator under Q30: step 12 now builds the step span for the in-memory and KurrentDB subscriptions, with a test.

### Step-3. The PostgreSQL retry and close paths run in no test

Quote: plan step 7: "The checkpoints and the subscription retry from step 6." Spec: "A subscription whose handler fails stops and resubscribes from its checkpoint after the workshop's `RetryBackOff`." The tests `aSubscriptionThatFailsRepeatedlyGetsTheEventAgainUntilItSucceeds` and `aClosedStoreStopsDeliveringAndRetrying` stayed in `KurrentDBEventStoreTests`; `DurableEventStoreTests` and `PostgreSQLEventStoreTests` do not have them.
Consequence: in `PostgreSQLSubscription`, `nextDelay` (with its reset branch), the `retryAt` back-off after more than one failure, `close()`, the `if (closed) return` guards in `poll` and `fail`, and the `SQLException` path in `nextEvents` have no test. If `close()` stopped working, an old subscription would run next to a new one and handle the same event twice, and nothing would fail. Fix: move the two tests into `DurableEventStoreTests` (the `newStore` and `close` hooks exist), or add them to `PostgreSQLEventStoreTests`.
Belongs to: implementation
Resolution: accepted by the coordinator under Q30: the SQLException and closed guards need a broken database connection; mocks are not allowed.

### Standards-1. The out-of-order commit test writes into storage with hand-written SQL

Quote: `PostgreSQLEventStoreTests.eventOfATransactionThatCommitsLastIsNotSkipped` and `insertItemAdded`: `"insert into events(stream_id, stream_position, id, type, data) values (?, 0, ?, ?, ?::jsonb)"`, `"insert into streams(id, stream_position) values (?, 0)"`, and a hand-built JSON string. AGENTS.md: tests reach the code "through the same entry points that calling code uses" and set up state "through the API too, not by writing into storage". Options: a package-private `appendIn(Connection, ...)` that the test calls (changes production code for tests), or keep the SQL and relax the rule for this one test. It is Oskar's decision.
Belongs to: implementation
Resolution: accepted by the coordinator under Q30: the test needs two open transactions at once, which `append` doesn't expose; the raw SQL is test setup that only this scenario needs.
