### Step-1. The nack and timeout paths of `awaitConfirm` are unreachable, and the changed behaviour has no test

Quote: `operations.send(route.target(), route.key(), message, correlation); waitForConfirms(operations);` followed by `awaitConfirm(route.target(), correlation)`, which holds `if (!confirm.ack()) throw new AmqpException("RabbitMQ did not accept the message: " + confirm.reason());` and `catch (TimeoutException e) { throw new AmqpTimeoutException("No publisher confirm from RabbitMQ within " + publishTimeout, e); }`. Spec line 227: "Publishing waits for the publisher confirm, with the workshop's publish timeout". Spec 11.1: the publish fails within the publish timeout.
Consequence:
- A nack: `waitForConfirmsOrDie` throws `IOException("nacks received")`, which Spring translates to `AmqpIOException`, so `send` throws before `awaitConfirm` runs. The "did not accept" branch and the broker reason can no longer be reached, and the client closes the channel on a nack (before, it stayed open).
- A timeout: the first wait now fires, so the `TimeoutException` branch is dead unless the future completes late. If it does, a publish can take up to twice the publish timeout, against spec 11.1. The caller probably no longer gets `AmqpTimeoutException` (depends on the library translation).
- Two overlapping confirm mechanisms exist where one is enough. Only the `returned` check in `awaitConfirm` still does work.
- No test runs a nack (`max-length=0` with reject-publish is set only on dead-letter queues) or expects the "No publisher confirm" timeout. The tests assert only `AmqpException` and a time below 10 s, so the change is unguarded.
- The new behaviour (a nack closes the publisher channel) is a decision on the work an operation does that the step, spec and qa do not state.
Belongs to: implementation. Keep one path: let `waitForConfirms` own nack and timeout and reduce `awaitConfirm` to the return check, or catch the translated exceptions in `send` and rethrow the old messages. Add a test for the timeout type. If the closed channel on a nack is accepted, state it in the spec or qa.
Resolution: fixed. There is one path now: `waitForConfirms` (inside `invoke`) owns the confirm, the nack and the timeout, and translates raw client exceptions to `AmqpException`; `awaitConfirm` is replaced by `failIfReturned`, which only checks the returned message. The old "did not accept" text with the broker reason is gone with the old path (the client closes the channel on a nack and the translated error carries its cause). No test forces a nack or reads the timeout type without a mock; the blocked-publisher and deleted-exchange tests check that each failure is an `AmqpException` (accepted).

### Step-2. The ordering of the return and the confirm has no test with a timeout set

Quote: `operations.send(route.target(), route.key(), message, correlation); waitForConfirms(operations);` then `correlation.getReturned()` after the wait.
Consequence: the unrouted-message check works only if the return callback fires before the confirm completes the wait. The test at `RabbitMQMessageBusTests` line 111 passes, so the common case holds. No test runs a mandatory send together with a publish timeout. Risk is low. Searched `spec.md` and `qa.md`: neither decides this case, and the gap is a missing test, so it is tagged `implementation`.
Belongs to: implementation
Resolution: accepted. A mandatory send together with a timeout cannot be forced without a mock; the return check runs after the confirm wait, as before.
