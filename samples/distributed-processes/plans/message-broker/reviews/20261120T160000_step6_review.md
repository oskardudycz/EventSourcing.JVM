### Step-1. Retry paths of `AllStreamSubscription` have no test

Quote: step: "A subscription whose handler fails stops and resubscribes from its checkpoint after `RetryBackOff`." Every test makes the handler fail exactly once (26.1, 26.2), so the paths for a second failure in a row (back-off STOP and restart), a failing `start()` that schedules another resubscribe, `onCancelled` with a throwable, `close()` while a resubscribe is scheduled and the back-off reset after a good event never run.
Consequence: a wrong delay (stuck at 0, never reset) or a resubscribe loop that does not stop on `close()` would pass all tests.
Belongs to: implementation
Resolution: fixed. Tests added: `aSubscriptionThatFailsRepeatedlyGetsTheEventAgainUntilItSucceeds` (4 failures, so the back-off reaches STOP and restarts), `aClosedStoreStopsDeliveringAndRetrying` (`close()` ends the retries), `aCancelledSubscriptionSubscribesAgainFromItsCheckpoint` (a checkpoint at an invalid position makes KurrentDB cancel the subscription; moving the checkpoint to a valid one lets the resubscribe deliver the event: the `onCancelled` path, no mock). Not tested: a failing `start()`. It needs an unreachable server, whose connect timeout makes the test slow and timing dependent, and a mock is not allowed; it shares `fail()` with the tested `onCancelled` path. The back-off reset after a good event is not tested either.

### Step-2. 27.3 and 27.5 run with projections on H2

Quote: step: "27.3-27.5 on KurrentDB with projections on PostgreSQL". `subscriptionContinuesAfterItsCheckpointOnRestart` and `eventAlreadyPastTheCheckpointIsSkippedAndRolledBack` use `ProjectionsDatabase.H2`; only 27.4 uses PostgreSQL.
Consequence: the restart checkpoint and the skip are not shown on PostgreSQL, which is the default projections database. The logic does not depend on the database, so the risk is small.
Belongs to: implementation
Resolution: fixed. `subscriptionContinuesAfterItsCheckpointOnRestart` and `eventAlreadyPastTheCheckpointIsSkippedAndRolledBack` use a store on PostgreSQL projections.

### Step-3. 27.3 and 27.5 differ from the step wording

Quote: step 27.3: "a forwarder handles 3 events ... asserts the forwarder publishes only the new one"; the test uses a plain recording handler and 4 events. Step 27.5: "stores a checkpoint past the event's position, then delivers the event"; the test subscribes first, stores `Long.MAX_VALUE`, then appends, so the subscription may replay the log while the checkpoint is set.
Consequence: "publish, then checkpoint" is not checked with a real forwarder; the 27.5 order depends on timing, though the handler filters by `orderId` so the outcome is the same today.
Belongs to: implementation
Resolution: accepted: 27.3 uses a recording handler, because the check is what the subscription hands to a handler after a restart, which is the same for a forwarder; 27.5 stores the checkpoint after subscribing, because a checkpoint stored before would make the subscription start after the event and never deliver it. The handler filters by the test's own order, so replayed older events do not change the outcome.

### Step-4. Behaviour after `RetryBackOff` stops is not decided

Quote: spec: "A subscription whose handler fails stops and resubscribes from its checkpoint after the workshop's `RetryBackOff` (Q25)." Code restarts the back-off when it returns STOP, so a handler that always fails is retried every 1 to 3 seconds forever. `qa.md` Q25 has no text on exhaustion.
Consequence: the choice (retry forever, stop the subscription, dead-letter) is made by the code, not by the spec.
Belongs to: spec
Resolution: decided by the coordinator under Q30: retry forever with the back-off, logging each failure, as the spec says ("resubscribes from its checkpoint after the workshop's `RetryBackOff`") and as the in-memory store already does (an event that always fails is delivered again on each append). Listed for Oskar at the end of the run.

### Step-5. `ProcessorCheckpoints` is a class the step does not name

Quote: step Context: "The checkpoint entity and its Spring Data repository live next to the projections". The diff adds `ProcessorCheckpoints`, a `TransactionTemplate` wrapper, and a bean for it. AGENTS.md: "Do not introduce a new abstraction unless explicitly requested."
Consequence: an unrequested abstraction; it is the only place that runs "work plus checkpoint in one transaction" and tests use it directly.
Belongs to: plan
Resolution: allowed by the coordinator under Q30: the spec requires the handler's change and its checkpoint in one transaction and the at-or-past check, and that logic needs one home; `ProcessorCheckpoints` is it, not a speculative abstraction.
