### Step-1. The retry loop in `close()` has no pause, and its exhausted path is not tested

Quote: `for (var attempt = 1; ; attempt++) { try { connectionFactory.destroy(); return; } catch (ConcurrentModificationException e) { if (attempt == DESTROY_ATTEMPTS) throw e; } }`. The test `closingRightAfterPublishingNeverFails` runs 300 times and calls `bus.close()` after each publish. Step 11 does not mention how `close()` behaves.
Consequence: the 5 attempts run back to back, while Spring AMQP returns the publisher channel asynchronously. On a loaded machine all 5 can fail within microseconds, and `close()` then throws the `ConcurrentModificationException`. The 300 rounds show the common case passes, not that 5 immediate retries are enough. No test runs the `attempt == DESTROY_ATTEMPTS` branch. `spec.md` and `qa.md` do not decide the behaviour of `close()`, but it is a shutdown detail inside the bus, not a behaviour a reader of the spec depends on, so it stays with the implementation.
Belongs to: implementation
Resolution: superseded. The retry loop failed in a full build with a `NullPointerException` from the same unsynchronized list, so it was removed. `send` now waits for the confirms inside `RabbitTemplate.invoke`, which returns the channel to the cache on the publishing thread; `close()` is a plain `destroy()` again. Before: the loop waited 50 ms between attempts (`DESTROY_RETRY_MILLIS`). The last attempt rethrows; no test reaches it, because the race cannot be forced without a mock (accepted).

### Standards-2. `closingRightAfterPublishingNeverFails` is probabilistic and slow

Quote: `for (var attempt = 0; attempt < 300; attempt++) { var bus = newBus(); bus.publish(...); bus.close(); }`
Consequence: a pass proves the race is gone only with some probability, and a rare failure shows up as a flaky test. Each round builds a new connection factory and declares the exchange, queue, dead-letter exchange and dead-letter queue, so 300 rounds are slow, and the number 300 has no stated reason. The test name follows the rule (behaviour from the caller's view).
Belongs to: implementation
Resolution: accepted. 100 rounds with one message did not fail, 300 rounds with two messages failed before the fix (measured), so 300 is the smallest count tried that shows the race; the test takes about 10 s.
