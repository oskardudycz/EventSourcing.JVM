### Step-1. The listed existing tests do not use a Spring context with the `in-memory` profile

Quote: Plan: "they keep their scenarios and get their repositories from a Spring context with the `in-memory` profile, on H2." Spec line 315: "`ECommerceTests`: keeps its scenarios and runs with the `in-memory` profile, on H2 through JPA." Diff, in `ECommerceTests`, `PaymentFacadeTests`, `PaymentTimeoutWorkerTests`, `AuthorizationExpiryWorkerTests` and `OrderFacadeTests`: `H2.repository(CustomerShoppingCartRepository.class)`. `ProjectionsDatabase.start` builds its own `SpringApplicationBuilder(Projections.class)` with `--projections.database=h2` and no profile.
Consequence: These tests never load `application-in-memory.properties`, so no test of this kind runs with the profile. The spec's "`ECommerceTests` runs with the `in-memory` profile" is met in name only. The helper context is shared by every test class in the JVM and is never closed. Scenarios are kept and the tests use H2, so the practical risk is low.
Belongs to: implementation
Resolution: open

### Step-2. Worker tests assert on everything in their own store, not only on their own IDs

Quote: Plan: "Worker tests (`PaymentTimeoutWorkerTests`, `AuthorizationExpiryWorkerTests`, the unpaid-orders tests): they assert only on the messages about their own new IDs, because the shared table holds other tests' documents." Diff: the two worker test files change only the constructor and imports. `published.shouldNotReceiveAnyEvent()`, `assertThat(published.published).hasSize(1)` and `shouldReceiveMessages(new PaymentTimedOut(paymentId, afterThreshold))` still cover all messages. Only `ECommerceTests` filters (`isAboutThisPurchase`). No unpaid-orders worker test was changed.
Consequence: Each test sees other tests' documents in the shared H2 table, and the worker publishes commands for those IDs to its own bus. The tests pass only because `Payment.timeOut` and `expireAuthorization` return early on an empty stream. If an aggregate emitted an event for an unknown stream, the tests would fail depending on test order. The other review axis found the same tests pass today (`containsOnlyOnce(orderId)`, `doesNotContain(orderId)` in the unpaid-orders tests), so the gap is in the payment worker tests.
Belongs to: implementation
Resolution: open

### Step-4. Each document write costs extra reads

Quote: `Projection.handle`: `repository.findById(id)`, then `repository.save(document)` or `repository.deleteById(id)`. The entities use assigned `@EmbeddedId` ids and have no `@Version`.
Consequence: `save` on an assigned id calls `merge`, which selects the row again, and `deleteById` selects before it deletes. Each event costs about two selects plus the write. The spec neither allows nor rules this out (searched for extra queries and round trips). Step 12's "one transaction with the checkpoint" will depend on it.
Belongs to: spec
Resolution: reclassified as implementation by the coordinator under Oskar's standing instruction (Q30): the spec already chose `findById`, `save` and `deleteById`; the extra reads come from how they are called, not from the spec. `Projection.handle` runs in one transaction and writes the entity it loaded (`save` on the managed entity, `delete(current)`), so each event costs one read and one write. Sent to the implementer to fix.
